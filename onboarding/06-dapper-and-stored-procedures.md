## When to Use Dapper vs EF Core

LoanSuperMarket uses **both** EF Core and Dapper, each for what it does best:

| Concern | EF Core | Dapper |
|---------|---------|--------|
| **Use case** | CRUD operations, domain logic | Reporting, analytics, dashboards |
| **Strengths** | Change tracking, relationships, migrations | Raw speed, complex SQL, aggregations |
| **Overhead** | Higher (object tracking, LINQ translation) | Minimal (thin mapper over ADO.NET) |
| **SQL control** | Generated by LINQ provider | You write the SQL directly |
| **Mapping** | Full entity with navigation properties | Flat DTOs (no tracking) |
| **Transactions** | Built-in via SaveChanges | Manual if needed |
| **Best for** | Write operations, simple reads | Multi-table JOINs, GROUP BY, aggregates |

### Our Decision Rule

```
Is this operation...
├── Creating, updating, or deleting data? → Use EF Core
├── A simple read by ID or filter? → Use EF Core
├── A complex report with aggregations? → Use Dapper + Stored Procedure
├── A dashboard with multiple KPIs? → Use Dapper + Stored Procedure
└── A read that joins 3+ tables with GROUP BY? → Use Dapper + Stored Procedure
```

### Why Not Just Use EF Core for Everything?

For the admin dashboard, we need to calculate:
- Total active loans
- Total funded amount
- Total collected payments
- Interest income
- Late fees collected
- Active lenders/borrowers count
- Available capital

Doing this with EF Core would generate multiple queries or one massive LINQ expression that
translates to inefficient SQL. A stored procedure does it in a **single optimized query** that
the database engine can cache and optimize.

### Why Not Just Use Dapper for Everything?

- No change tracking (you'd have to write UPDATE statements manually)
- No migrations (schema changes are manual)
- No relationship loading (no Include/ThenInclude)
- No LINQ (all SQL is hand-written strings)
- No value object mapping (no OwnsOne)

**Bottom line:** EF Core for the domain, Dapper for reporting.

## IPlatformReportService Interface

The interface lives in the Application layer, defining what reports are available without
specifying how they're implemented.

```csharp
// File: src/LoanSuperMarket.Application/Common/Interfaces/IPlatformReportService.cs

using LoanSuperMarket.Shared.Dashboard;

namespace LoanSuperMarket.Application.Common.Interfaces;

/// <summary>
/// High-performance reporting service using stored procedures via Dapper.
/// </summary>
public interface IPlatformReportService
{
    /// <summary>
    /// Returns platform-wide KPIs: active loans, total funded, collections, etc.
    /// Used by the admin dashboard.
    /// </summary>
    Task<PlatformSummaryDto> GetPlatformSummaryAsync(
        CancellationToken cancellationToken = default);

    /// <summary>
    /// Returns monthly interest income breakdown for a specific lender.
    /// Used by the lender earnings/analytics pages.
    /// </summary>
    Task<IReadOnlyList<MonthlyInterestReportDto>> GetMonthlyInterestReportAsync(
        Guid lenderId,
        DateTime fromDate,
        DateTime toDate,
        CancellationToken cancellationToken = default);
}
```

### Why an Interface?

1. **Testability** — You can mock `IPlatformReportService` in unit tests without a database
2. **Clean Architecture** — Application layer doesn't know about Dapper or SQL
3. **Swappability** — Could replace Dapper with raw ADO.NET, a different ORM, or even an API call
4. **Dependency Inversion** — High-level modules don't depend on low-level details

### Interface Design Principles

- Methods return **DTOs**, not domain entities (reports are read-only projections)
- All methods are **async** with `CancellationToken` support
- Return types use `IReadOnlyList<T>` for collections (immutable contract)
- Method names describe the **business operation**, not the implementation

## DapperPlatformReportService Implementation

The full implementation with detailed explanations:

```csharp
// File: src/LoanSuperMarket.Infrastructure/Services/DapperPlatformReportService.cs

using System.Data;
using Dapper;
using LoanSuperMarket.Application.Common.Interfaces;
using LoanSuperMarket.Shared.Dashboard;
using Microsoft.Data.SqlClient;
using Microsoft.Extensions.Configuration;

namespace LoanSuperMarket.Infrastructure.Services;

/// <summary>
/// High-performance reporting using Dapper and stored procedures.
/// Bypasses EF Core for read-heavy aggregation queries.
/// </summary>
public sealed class DapperPlatformReportService : IPlatformReportService
{
    private readonly string _connectionString;

    // ─── Constructor ────────────────────────────────────────────────────
    // Injects IConfiguration to read the connection string.
    // We store the string, not a DbContext — Dapper manages its own connections.
    public DapperPlatformReportService(IConfiguration configuration)
    {
        _connectionString = configuration.GetConnectionString("DefaultConnection")
            ?? throw new InvalidOperationException("DefaultConnection not configured.");
    }

    // ─── Method 1: Platform Summary ────────────────────────────────────
    // Calls sp_GetPlatformSummary which returns a single row of KPIs.
    public async Task<PlatformSummaryDto> GetPlatformSummaryAsync(
        CancellationToken cancellationToken = default)
    {
        // 1. Create a new SQL connection (Dapper extends IDbConnection)
        await using var connection = new SqlConnection(_connectionString);

        // 2. Execute the stored procedure and map the single result row
        var result = await connection.QueryFirstOrDefaultAsync<PlatformSummaryDto>(
            "sp_GetPlatformSummary",                    // Stored procedure name
            commandType: CommandType.StoredProcedure);  // Tell Dapper it's a sproc

        // 3. Return result or empty DTO (never null)
        return result ?? new PlatformSummaryDto();
    }

    // ─── Method 2: Monthly Interest Report ─────────────────────────────
    // Calls sp_GetMonthlyInterestReport with parameters.
    // Returns multiple rows (one per month).
    public async Task<IReadOnlyList<MonthlyInterestReportDto>> GetMonthlyInterestReportAsync(
        Guid lenderId, DateTime fromDate, DateTime toDate,
        CancellationToken cancellationToken = default)
    {
        // 1. Create connection
        await using var connection = new SqlConnection(_connectionString);

        // 2. Execute with parameters (anonymous object maps to SQL parameters)
        var results = await connection.QueryAsync<MonthlyInterestReportDto>(
            "sp_GetMonthlyInterestReport",
            new { LenderId = lenderId, FromDate = fromDate, ToDate = toDate },
            commandType: CommandType.StoredProcedure);

        // 3. Materialize to list
        return results.ToList();
    }
}
```

### Key Implementation Details

1. **Connection per call** — Each method creates its own `SqlConnection`. This is intentional:
   - Connections are pooled by ADO.NET (creating is cheap)
   - No shared state between calls
   - Thread-safe by design

2. **`await using`** — Ensures the connection is disposed (returned to pool) even if an
   exception occurs.

3. **No explicit Open()** — Dapper automatically opens the connection when you call
   `QueryAsync` or `QueryFirstOrDefaultAsync`.

4. **Anonymous objects for parameters** — `new { LenderId = lenderId, FromDate = fromDate }`
   maps C# properties to SQL parameters `@LenderId`, `@FromDate`, `@ToDate`.

5. **CommandType.StoredProcedure** — Tells Dapper to execute `EXEC sp_Name @Param1, @Param2`
   rather than treating the string as raw SQL.

6. **Null safety** — `result ?? new PlatformSummaryDto()` ensures we never return null.

## Connection String Management

### Where It's Defined

```json
// File: src/LoanSuperMarket.Api/appsettings.json

{
  "ConnectionStrings": {
    "DefaultConnection": "Server=DESKTOP-VVJN96B;Database=LoanSuperMarketDb;Trusted_Connection=True;MultipleActiveResultSets=true;TrustServerCertificate=True"
  }
}
```

### How Dapper Gets It

Unlike EF Core (which gets a pre-configured `DbContextOptions`), Dapper reads the connection
string directly from `IConfiguration`:

```csharp
public DapperPlatformReportService(IConfiguration configuration)
{
    _connectionString = configuration.GetConnectionString("DefaultConnection")
        ?? throw new InvalidOperationException("DefaultConnection not configured.");
}
```

### Connection String Components

| Component | Value | Purpose |
|-----------|-------|---------|
| `Server` | `DESKTOP-VVJN96B` | SQL Server instance name |
| `Database` | `LoanSuperMarketDb` | Database name |
| `Trusted_Connection` | `True` | Windows Authentication (no password) |
| `MultipleActiveResultSets` | `true` | Allow multiple queries on one connection |
| `TrustServerCertificate` | `True` | Skip SSL certificate validation (dev only) |

### Important: Same Connection String as EF Core

Both EF Core and Dapper use the **same** `DefaultConnection` string. They hit the same
database — they just use different access patterns:

```
appsettings.json → "DefaultConnection"
    ├── EF Core: DbContextOptions<ApplicationDbContext> (via DI)
    └── Dapper: IConfiguration.GetConnectionString() (direct read)
```

### Connection Pooling

ADO.NET automatically pools connections. When you call `new SqlConnection(connectionString)`,
it doesn't actually create a new TCP connection — it grabs one from the pool. When you
dispose the connection, it returns to the pool. This means:

- Creating connections is **cheap** (microseconds)
- You should create connections **per operation** (not shared)
- The pool handles the expensive TCP/TLS handshakes

## Stored Procedures

### sp_GetPlatformSummary

Returns platform-wide KPIs in a single query. Used by the admin dashboard.

```sql
-- File: src/LoanSuperMarket.Infrastructure/Persistence/StoredProcedures/sp_GetPlatformSummary.sql

-- Stored Procedure: Platform Summary Dashboard
-- Returns high-level platform KPIs in a single query
-- Usage: EXEC sp_GetPlatformSummary

CREATE OR ALTER PROCEDURE [dbo].[sp_GetPlatformSummary]
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        -- Active loans: schedules not in default status (Performance != 3)
        (SELECT COUNT(*)
         FROM RepaymentSchedules
         WHERE Performance != 3) AS ActiveLoans,

        -- Defaulted loans: schedules in default status
        (SELECT COUNT(*)
         FROM RepaymentSchedules
         WHERE Performance = 3) AS DefaultedLoans,

        -- Total amount funded across all loans
        (SELECT ISNULL(SUM(FundedAmount), 0)
         FROM RepaymentSchedules) AS TotalFunded,

        -- Total payments collected (from paid installments)
        (SELECT ISNULL(SUM(i.PaidAmount), 0)
         FROM Installments i
         WHERE i.[Status] = 2) AS TotalCollected,

        -- Total interest income collected
        (SELECT ISNULL(SUM(i.InterestPortion), 0)
         FROM Installments i
         WHERE i.[Status] = 2) AS TotalInterestCollected,

        -- Total late fees collected
        (SELECT ISNULL(SUM(i.LateFeeAmount), 0)
         FROM Installments i
         WHERE i.[Status] = 2 AND i.LateFeeAmount > 0) AS TotalLateFeesCollected,

        -- Number of verified/active lenders (Status = 3)
        (SELECT COUNT(*)
         FROM Lenders
         WHERE [Status] = 3) AS ActiveLenders,

        -- Number of verified/active borrowers (Status = 3)
        (SELECT COUNT(*)
         FROM Borrowers
         WHERE [Status] = 3) AS ActiveBorrowers,

        -- Total capital available for lending
        (SELECT ISNULL(SUM(AvailableFunds), 0)
         FROM Lenders
         WHERE [Status] = 3) AS TotalAvailableCapital;
END
GO
```

### sp_GetMonthlyInterestReport

Returns monthly interest income breakdown for a specific lender.

```sql
-- File: src/LoanSuperMarket.Infrastructure/Persistence/StoredProcedures/sp_GetMonthlyInterestReport.sql

-- Stored Procedure: Monthly Interest Report
-- Returns aggregated interest income per lender per month
-- Usage: EXEC sp_GetMonthlyInterestReport @LenderId, @FromDate, @ToDate

CREATE OR ALTER PROCEDURE [dbo].[sp_GetMonthlyInterestReport]
    @LenderId UNIQUEIDENTIFIER,
    @FromDate DATE,
    @ToDate DATE
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        rs.LenderId,
        YEAR(i.PaidDate) AS [Year],
        MONTH(i.PaidDate) AS [Month],
        COUNT(i.Id) AS PaidInstallments,
        SUM(i.InterestPortion) AS TotalInterestIncome,
        SUM(i.PrincipalPortion) AS TotalPrincipalReturned,
        SUM(i.LateFeeAmount) AS TotalLateFees,
        SUM(i.InterestPortion + i.LateFeeAmount) AS TotalIncome
    FROM Installments i
    INNER JOIN RepaymentSchedules rs ON i.RepaymentScheduleId = rs.Id
    WHERE rs.LenderId = @LenderId
        AND i.[Status] = 2          -- Only paid installments
        AND i.PaidDate IS NOT NULL
        AND i.PaidDate >= @FromDate
        AND i.PaidDate <= @ToDate
    GROUP BY rs.LenderId, YEAR(i.PaidDate), MONTH(i.PaidDate)
    ORDER BY [Year] DESC, [Month] DESC;
END
GO
```

### Stored Procedure Design Patterns

1. **`SET NOCOUNT ON`** — Suppresses "X rows affected" messages, reducing network traffic
2. **`ISNULL(SUM(...), 0)`** — Returns 0 instead of NULL when no rows match
3. **`CREATE OR ALTER`** — Idempotent: safe to run multiple times (creates or updates)
4. **Column aliases match DTO properties** — `AS ActiveLoans` maps to `PlatformSummaryDto.ActiveLoans`
5. **Parameterized** — Uses `@LenderId`, `@FromDate`, `@ToDate` (prevents SQL injection)
6. **Status as integers** — `[Status] = 2` means "Paid", `Performance = 3` means "Defaulted"

### How to Deploy Stored Procedures

Stored procedures are **not managed by EF Core migrations**. Deploy them manually:

```bash
# Option 1: Run in SQL Server Management Studio (SSMS)
# Open the .sql file and execute

# Option 2: Use sqlcmd
sqlcmd -S DESKTOP-VVJN96B -d LoanSuperMarketDb -i sp_GetPlatformSummary.sql

# Option 3: Add to a migration (if you want version control)
# In a migration's Up() method:
migrationBuilder.Sql(@"
    CREATE OR ALTER PROCEDURE [dbo].[sp_GetPlatformSummary]
    AS
    BEGIN
        -- ... procedure body ...
    END
");
```

## Dapper Query Patterns

Dapper provides several extension methods on `IDbConnection`. Here are the ones used in this
project and others you'll commonly need:

### QueryFirstOrDefaultAsync<T> — Single Row

Returns the first row mapped to `T`, or `default(T)` if no rows.

```csharp
// Used for: single-row results (dashboard summary, entity by ID)
var result = await connection.QueryFirstOrDefaultAsync<PlatformSummaryDto>(
    "sp_GetPlatformSummary",
    commandType: CommandType.StoredProcedure);
```

**When to use:** When you expect exactly one row (or none).

### QueryAsync<T> — Multiple Rows

Returns all rows mapped to `IEnumerable<T>`.

```csharp
// Used for: multi-row results (monthly reports, lists)
var results = await connection.QueryAsync<MonthlyInterestReportDto>(
    "sp_GetMonthlyInterestReport",
    new { LenderId = lenderId, FromDate = fromDate, ToDate = toDate },
    commandType: CommandType.StoredProcedure);

return results.ToList();
```

**When to use:** When you expect zero or more rows.

### QuerySingleAsync<T> — Exactly One Row (Throws if Not Found)

```csharp
// Throws InvalidOperationException if no rows or multiple rows
var loan = await connection.QuerySingleAsync<LoanDetailDto>(
    "SELECT Id, Title, Amount FROM LoanProducts WHERE Id = @Id",
    new { Id = productId });
```

**When to use:** When the row MUST exist (throws if it doesn't).

### ExecuteAsync — No Result (INSERT, UPDATE, DELETE)

```csharp
// Returns the number of affected rows
var rowsAffected = await connection.ExecuteAsync(
    "UPDATE Installments SET ReminderSent = 1 WHERE Id = @Id",
    new { Id = installmentId });
```

**When to use:** For write operations (rare with Dapper in this project — we use EF Core for writes).

### QueryMultipleAsync — Multiple Result Sets

```csharp
// Execute a procedure that returns multiple SELECT statements
await using var multi = await connection.QueryMultipleAsync(
    "sp_GetDashboardData",
    new { UserId = userId },
    commandType: CommandType.StoredProcedure);

var summary = await multi.ReadFirstOrDefaultAsync<DashboardSummary>();
var recentLoans = (await multi.ReadAsync<RecentLoanDto>()).ToList();
var notifications = (await multi.ReadAsync<NotificationDto>()).ToList();
```

**When to use:** When a stored procedure returns multiple result sets in one call.

### Inline SQL vs Stored Procedures

```csharp
// ─── Stored Procedure (preferred for complex queries) ───────────────
var result = await connection.QueryAsync<ReportDto>(
    "sp_GetMonthlyReport",
    new { Year = 2024 },
    commandType: CommandType.StoredProcedure);

// ─── Inline SQL (acceptable for simple queries) ─────────────────────
var result = await connection.QueryAsync<LoanDto>(
    @"SELECT Id, Title, InterestRate
      FROM LoanProducts
      WHERE LenderId = @LenderId AND Status = @Status",
    new { LenderId = lenderId, Status = (int)LoanProductStatus.Published });
```

### Parameter Mapping Rules

Dapper maps anonymous object properties to SQL parameters by name:

```csharp
// C# anonymous object          →  SQL parameters
new {
    LenderId = lenderId,        →  @LenderId
    FromDate = fromDate,        →  @FromDate
    ToDate = toDate             →  @ToDate
}
```

- Property names must match parameter names (case-insensitive)
- Types are automatically converted (Guid → UNIQUEIDENTIFIER, DateTime → DATE, etc.)
- Null values are passed as DBNull

### Column-to-Property Mapping

Dapper uses **case-insensitive name matching**:

```sql
-- SQL column alias          →  C# property
SELECT
    COUNT(*) AS ActiveLoans  →  PlatformSummaryDto.ActiveLoans
    SUM(FundedAmount) AS TotalFunded  →  PlatformSummaryDto.TotalFunded
```

### DTO Design Rules

1. **Public setters** — Dapper needs to set properties (unlike domain entities)
2. **Simple types only** — No navigation properties, no value objects
3. **Flat structure** — One DTO per result set (no nesting)
4. **Lives in Shared project** — DTOs are used by both API and Blazor client
5. **No constructor parameters** — Dapper uses the parameterless constructor

### Why DTOs Live in the Shared Project

```
LoanSuperMarket.Shared/Dashboard/PlatformSummaryDto.cs
    ├── Used by: Infrastructure (Dapper maps to it)
    ├── Used by: Application (returned from interface)
    ├── Used by: API (serialized to JSON)
    └── Used by: Blazor (deserialized from JSON)
```

The Shared project is referenced by all layers, making DTOs available everywhere without
circular dependencies.

## Dependency Injection Registration

The Dapper service is registered in the Infrastructure layer's DI configuration:

```csharp
// File: src/LoanSuperMarket.Infrastructure/DependencyInjection.cs (relevant section)

// Dapper-based reporting (stored procedures)
services.AddScoped<IPlatformReportService, DapperPlatformReportService>();
```

### Why Scoped?

- **Scoped** = one instance per HTTP request
- The service holds a connection string (lightweight), not an open connection
- Connections are created per method call and disposed immediately
- Scoped aligns with how EF Core contexts are registered (consistency)

### How It's Consumed

In a MediatR handler or controller:

```csharp
public sealed class GetPlatformSummaryQueryHandler
    : IRequestHandler<GetPlatformSummaryQuery, PlatformSummaryDto>
{
    private readonly IPlatformReportService _reportService;

    public GetPlatformSummaryQueryHandler(IPlatformReportService reportService)
    {
        _reportService = reportService;
    }

    public async Task<PlatformSummaryDto> Handle(
        GetPlatformSummaryQuery request,
        CancellationToken cancellationToken)
    {
        return await _reportService.GetPlatformSummaryAsync(cancellationToken);
    }
}
```

The handler doesn't know (or care) that Dapper is being used. It just calls the interface.

## How to Add a New Report Step-by-Step

Let's add a new report: "Top Performing Lenders" that returns the top N lenders by total
interest earned.

### Step 1: Create the DTO

```csharp
// File: src/LoanSuperMarket.Shared/Dashboard/TopLenderDto.cs

namespace LoanSuperMarket.Shared.Dashboard;

public sealed class TopLenderDto
{
    public Guid LenderId { get; set; }
    public string CompanyName { get; set; } = string.Empty;
    public int ActiveLoans { get; set; }
    public decimal TotalFunded { get; set; }
    public decimal TotalInterestEarned { get; set; }
    public decimal DefaultRate { get; set; }
}
```

### Step 2: Write the Stored Procedure

```sql
-- File: src/LoanSuperMarket.Infrastructure/Persistence/StoredProcedures/sp_GetTopLenders.sql

CREATE OR ALTER PROCEDURE [dbo].[sp_GetTopLenders]
    @TopN INT = 10
AS
BEGIN
    SET NOCOUNT ON;

    SELECT TOP (@TopN)
        l.Id AS LenderId,
        l.CompanyName,
        COUNT(CASE WHEN rs.Performance != 3 THEN 1 END) AS ActiveLoans,
        ISNULL(SUM(rs.FundedAmount), 0) AS TotalFunded,
        ISNULL(SUM(
            (SELECT ISNULL(SUM(i.InterestPortion), 0)
             FROM Installments i
             WHERE i.RepaymentScheduleId = rs.Id AND i.[Status] = 2)
        ), 0) AS TotalInterestEarned,
        CASE
            WHEN COUNT(rs.Id) = 0 THEN 0
            ELSE CAST(COUNT(CASE WHEN rs.Performance = 3 THEN 1 END) AS DECIMAL(5,2))
                 / COUNT(rs.Id) * 100
        END AS DefaultRate
    FROM Lenders l
    LEFT JOIN RepaymentSchedules rs ON rs.LenderId = l.Id
    WHERE l.[Status] = 3  -- Active lenders only
    GROUP BY l.Id, l.CompanyName
    ORDER BY TotalInterestEarned DESC;
END
GO
```

### Step 3: Add Method to the Interface

```csharp
// File: src/LoanSuperMarket.Application/Common/Interfaces/IPlatformReportService.cs

    Task<PlatformSummaryDto> GetPlatformSummaryAsync(CancellationToken cancellationToken = default);

    // ⚡ NEW METHOD
    Task<IReadOnlyList<TopLenderDto>> GetTopLendersAsync(
        int topN = 10, CancellationToken cancellationToken = default);
```

### Step 4: Implement in DapperPlatformReportService

```csharp
// Add to: src/LoanSuperMarket.Infrastructure/Services/DapperPlatformReportService.cs

public async Task<IReadOnlyList<TopLenderDto>> GetTopLendersAsync(

{

```

```csharp
namespace LoanSuperMarket.Application.Features.Dashboard.GetTopLenders;
```

## Performance Benefits

### Why Stored Procedures Are Faster

1. **Pre-compiled execution plan** — SQL Server compiles and caches the execution plan on first
   run. Subsequent calls skip the compilation step entirely.

2. **Single round-trip** — One network call returns all KPIs. EF Core might generate multiple
   queries for the same data.

3. **No object tracking** — Dapper maps directly to DTOs without EF Core's change tracker
   overhead (which allocates memory for every entity loaded).

4. **Optimized SQL** — Hand-written SQL can use database-specific optimizations (indexed views,
   query hints) that LINQ can't express.

5. **Reduced data transfer** — SELECT only the columns you need, not entire entities with all
   their properties.

### Benchmark Comparison (Approximate)

| Operation | EF Core | Dapper + SP |
|-----------|---------|-------------|
| Platform summary (9 KPIs) | ~45ms (multiple queries) | ~8ms (single query) |
| Monthly report (12 months) | ~30ms (LINQ + GroupBy) | ~5ms (pre-compiled) |
| Memory allocation | ~2KB (tracked entities) | ~200 bytes (flat DTOs) |

### When Performance Matters Most

- **Dashboard pages** — Loaded on every login, must be fast
- **Analytics pages** — Complex aggregations over large datasets
- **Export/reporting** — Bulk data retrieval
- **Real-time widgets** — Polled frequently (every 30s)

### When Performance Doesn't Matter (Use EF Core)

- **Single entity CRUD** — Creating/updating one loan product
- **Simple lookups** — Get borrower by ID
- **Infrequent operations** — Admin actions performed rarely

## Common Pitfalls

### 1. Column Name Mismatch

If your SQL alias doesn't match the DTO property name, the value will be `default`:

```sql
-- ❌ BAD: "Total_Funded" won't map to "TotalFunded"
SELECT SUM(FundedAmount) AS Total_Funded FROM RepaymentSchedules

-- ✅ GOOD: Exact match (case-insensitive)
SELECT SUM(FundedAmount) AS TotalFunded FROM RepaymentSchedules
```

### 2. Forgetting CommandType.StoredProcedure

```csharp
// ❌ BAD: Dapper treats "sp_GetPlatformSummary" as raw SQL (fails)
var result = await connection.QueryFirstOrDefaultAsync<PlatformSummaryDto>(
    "sp_GetPlatformSummary");

// ✅ GOOD: Tells Dapper to execute as stored procedure
var result = await connection.QueryFirstOrDefaultAsync<PlatformSummaryDto>(
    "sp_GetPlatformSummary",
    commandType: CommandType.StoredProcedure);
```

### 3. Not Handling Null Results

```csharp
// ❌ BAD: QueryFirstOrDefaultAsync can return null
var result = await connection.QueryFirstOrDefaultAsync<PlatformSummaryDto>(...);
return result;  // Could be null!

// ✅ GOOD: Provide a fallback
return result ?? new PlatformSummaryDto();
```

### 4. Not Disposing Connections

```csharp
// ❌ BAD: Connection leak
var connection = new SqlConnection(_connectionString);
var result = await connection.QueryAsync<Dto>(...);
return result.ToList();
// Connection never disposed!

// ✅ GOOD: await using ensures disposal
await using var connection = new SqlConnection(_connectionString);
var result = await connection.QueryAsync<Dto>(...);
return result.ToList();
```

### 5. Using Dapper for Write Operations

```csharp
// ❌ BAD: Bypasses domain logic, no change tracking, no audit
await connection.ExecuteAsync(
    "UPDATE LoanApplications SET Status = 4 WHERE Id = @Id",
    new { Id = applicationId });

// ✅ GOOD: Use EF Core + domain methods for writes
var application = await _context.LoanApplications.FindAsync(applicationId);
application.Approve("Approved", "admin@demo.com");
await _context.SaveChangesAsync();
```

### 6. Stored Procedure Not Deployed

If you get "Could not find stored procedure 'sp_GetPlatformSummary'":
- The procedure hasn't been created in the database
- Run the SQL script manually or add it to a migration
- Check you're connected to the correct database

### 7. Parameter Type Mismatch

```csharp
// ❌ BAD: Passing string where UNIQUEIDENTIFIER expected
new { LenderId = "not-a-guid" }

// ✅ GOOD: Pass the correct type
new { LenderId = Guid.Parse("...") }
// Or better: use a Guid variable directly
new { LenderId = lenderId }  // where lenderId is Guid
```
